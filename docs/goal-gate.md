# ゴール定義ゲート（原子ツリーに入る前の関所）

原子ツリーは「**渡されたゴールを正しく割れているか**」しか見ない。未熟なゴールを渡せば、未熟なまま律儀に
割られ、ずれは実装が終わった後に手戻りとして出る。このゲートはその手前に置き、ゴールが割るに足るかを
着手前に判定する。

**このファイルがゲートの正**。問い・却下条件・照合・分岐の文言はここが唯一の基準で、案件の途中で
緩めてはならない（AGENTS.md「検証の規律」＝基準は着手前に固定し、都合よく動かさない）。

## 三段構成（本人採点をしない）

| 段 | 誰 | 何をする |
|---|---|---|
| 1 | サブA（`goal-drafter`） | 依頼から8つの問いに答える。分からない事は埋めず「未確認」と書く |
| 2 | サブB（`basis-reviewer`） | 却下条件を1個ずつ当て、3本の照合を見る。**通すことが仕事ではない。迷ったら却下** |
| 3 | 人間（マスター） | B が出した争点に対し「直させる／通す（理由を記録）」を選ぶ |

- **A と B は必ず別のサブエージェントにする。** 同じセッションが自分で書いて自分で採点する形（＝本人採点）は
  AGENTS.md が最も強く禁じている。
- **B に渡すのは「A の答え」と「この文書」だけ**。なぜ通したいか等の事情は渡さない（同調を避ける）。
- **B は止めるだけで、覆さない。** 覆せるのは人間だけで、覆したときは理由を記録する。
- **合否だけを人間に見せない。** B の出力は「争点1文＋2択」にする（押す物ではなく、選ぶ物にする）。

## 8つの問い（Q1〜Q7 は固定。Q8 は実測から追加）

| | 問い | 却下条件（これに当たれば不合格） |
|---|---|---|
| Q1 | 顧客は誰か | 「みんな」「企業」。買う人と使う人を区別していない |
| Q2 | 顧客の問題は何か | 解を問題に偽装している。定量化がない。なぜ今かがない |
| Q3 | 最も重要な便益を1つ | 機能列挙。便益が2つ以上競合している（＝核が未定の証拠） |
| Q4 | なぜそう分かるのか | 逸話1件。「分かってる」。否定する証拠を探していない |
| Q5 | 体験はどう見えるか | 理想経路しかない。失敗経路が書かれていない |
| Q6 | 何をやらないのか | ゴールになり得たが外したものと、その理由が書かれていない |
| Q7 | どう渡すか | 納品形態と引き継ぎ先が書かれていない |
| Q8 | それは作れるのか | 権限・外部制約・依存先の可否を確認していない。「たぶんできる」。実物で1回も試していない |

- Q1〜Q5 の出典は Amazon の Working Backwards、Q6 は Google の design doc における非ゴール、
  Q7 は同社内 FAQ。項目数の上限（5〜9）は Atul Gawande『The Checklist Manifesto』。
- **Q8 は実測から足した**：`docs/failures.md:145`（「ブラウザ1クリックで設定」ボタンが、自動トークンに
  その権限が無く原理的に作れなかった）は Q1〜Q7 のどれを通しても素通りする。あれはゴールの完成度ではなく
  実現可能性の欠落だった。**「渡し方」を訊く Q7 は、その渡し方が成立するかまでは訊いていない。**

## 突き合わせ3本（判断ではなく、答え同士の照合）

賢い読み手を必要としない。線が繋がらない箇所が、そのまま書き直す箇所になる。

- **CHK 1**：Q3 の便益は、Q2 の問題を解いているか
- **CHK 2**：Q5 の体験は、Q3 の便益を Q1 の顧客に届けているか
- **CHK 3**：Q4 の証拠は、Q2 と Q3 を支えているか

1本でも切れていれば**ゴール未確定**。原子ツリーに進まず、A に書き直させる（＝戻り線。通行止めではない）。

## Q4 の証拠が取れない場合（3分岐）

ゲートが要求しているのは**証拠の存在ではない**。持っていない証拠を持っているふりをさせないこと。
取れなくても進めるが、取れなかったという事実だけは消えなくなる。

1. **分岐1｜代替証拠を取る** — 回数だけ聞く／業務データの差分を見る 等。取れたら確定。
2. **分岐2｜作らずに反証する** — 「仮定」と札を貼り、**反証の方法と判定期限を先に固定**して短期で試す。
   土台が崩れたらゴールを作り直す（開発コスト0で回避）。耐えたら確定。
3. **分岐3｜人間の事業判断** — 反証も打てない場合のみ。承知で作る／範囲を狭める／断る、のいずれかを
   **人間が**選び、判断者と日付を記録する。**ここに AI は入らない。**

### 状態の3種（記録に残す）

| 状態 | 書くこと |
|---|---|
| 実証済み | 証拠の内容と出所 |
| 仮定／反証テストあり | 仮定の内容、反証の方法、判定期限。**期限が来たら必ず判定する** |
| 仮定／未検証で着手 | 判断者と判断日。失敗した時に理由が即座に辿れるように |

## 記録先は `docs/roadmap.html` の `meta.goalgate`（別ファイルに書かない）

回答を独立ファイルに置くと、未マージのまま消える（`docs/failures.md:8` と同型の事故）。**毎PRで必ず
main に乗る `docs/roadmap.html` に同梱する。**

```json
"goalgate": {
  "answers": { "q1": "…", "q2": "…", "q3": "…", "q4": "…",
               "q5": "…", "q6": "…", "q7": "…", "q8": "…" },
  "checks":  { "chk1": "成立", "chk2": "成立", "chk3": "仮定" },
  "evidence_state": "実証済み | 仮定/反証テストあり | 仮定/未検証で着手",
  "assumption": "仮定の内容（実証済みなら空）",
  "falsify": "反証の方法（同上）",
  "deadline": "判定期限（同上）",
  "judged_by": "覆した人と日付・理由（人間が通した場合のみ）"
}
```

## この仕組み自体の未確定事項（消さずに残す）

このゲートは、**実案件で一度も走っていない**。効果の大きさは未実測である。

- 支える側：失敗ログ29件のうち6件（`:46` `:85` `:101` `:114` `:145` `:381`）がゴール定義起因。
- 反証側：そのうち最大の1件（`:114`）は「検問所を足したこと自体」が失敗だった事例。ただしあれは
  **変更のたび**に止まる仕組みで、このゲートは**案件あたり1回**。頻度が違う。
- 反証側：`:145` は Q8 を足しても「実物で1回試す」が要ると言っている。このゲート自身がまだ試されていない。

**したがって最初の1案件は、効果を測るための実行でもある。** 通した後、7〜8問で露見した項目を数え、
それぞれ「ゲートを通さずツリーだけを描いた場合、実装後まで残ったと言えるか」を `docs/failures.md`
または本節に追記する。0件ならこのゲートは不要（ツリーだけで足りる）。
